## Summary

The reviewed changes are structurally sound, but three correctness risks remain. The largest one is functional: the new video fallback path is not actually reachable in production because pathway selection is still gated behind a process-local default that only tests mutate. The second issue is that the pathway is chosen inside the async worker from that mutable global, which makes queued-job behavior nondeterministic if the default ever changes at runtime. One test also introduces a brittle timing assertion that is likely to flap on slower CI hosts.

I could not execute the test suite in this environment because `python3 -m pytest` failed with `No module named pytest`.

## Warnings

### WR-01: Video Fallback Is Not Reachable Outside Tests

**File:** `backend/services/pathway_config.py:7-34`
**Issue:** `DEFAULT_PATHWAY` is hardcoded to `"text"`, and `resolve_runtime_pathway()` only returns `"video"` when that module-global is flipped. A repo-wide reference check shows `set_default_pathway()` is only called from tests, so production code never enables the new video branch. As shipped, visual content will continue to use the text path even after this phase.
**Fix:**
```python
# backend/core/config.py
class Settings(BaseSettings):
    tribev2_default_pathway: Literal["text", "video"] = "text"

# backend/services/pathway_config.py
from backend.core.config import settings

def resolve_runtime_pathway(content: Content) -> str:
    if settings.tribev2_default_pathway == "video" and content_supports_video_fallback(content):
        return "video"
    return "text"
```

### WR-02: Queued Jobs Read Pathway Selection Too Late

**File:** `backend/core/queue.py:179`, `backend/services/pathway_config.py:18-24`
**Issue:** The worker resolves the pathway during `_process_job()`, not when the job is created. If the default pathway changes while a job is waiting in `gpu_queue`, the same request can be processed with a different pathway than intended at submission time. Because the switch is a mutable module-global, this also becomes inconsistent across multiple worker processes.
**Fix:**
```python
# Persist the chosen pathway when the job is created.
job.requested_pathway = resolve_runtime_pathway(content)

# Then use the persisted value in the worker.
selected_pathway = job.requested_pathway
```
Store the immutable choice on `Job` or in `job.input_path/result_json` metadata at enqueue time, rather than consulting mutable process state inside the worker.

### WR-03: `elapsed < 0.1` Makes `test_analyze` Timing-Dependent

**File:** `tests/test_analyze.py:221-228`
**Issue:** The test asserts the initial `/analyze` request completes in under 100 ms. That depends on machine load, SQLite latency, and event-loop scheduling rather than product behavior, so it is likely to flap in CI or on slower developer machines even when the queue wiring is correct.
**Fix:**
```python
response = await client.post(
    "/analyze",
    json={"persona_id": persona_fixture, "content_id": text_content_fixture},
)
assert response.status_code == 201
payload = response.json()
assert payload["status"] == "PENDING"

final = await _wait_for_terminal(client, payload["job_id"])
assert final["status"] == "DONE"
```
If you want to prove the request is non-blocking, assert on queue state or mocked background-call ordering instead of a wall-clock threshold.
